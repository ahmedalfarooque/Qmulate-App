# 14 · Reporting & dashboards spec

The build-facing spec for QMULATE's read surfaces: the compliance dashboard that surfaces the five zero-tolerance KPIs, the class-appropriate financial reports, the auditor/regulator **evidence-pack export**, and the reporting-cadence packs.

Status: Draft v0.1 · Privileged & Confidential

This section turns the BRD's reporting requirements ([BR-901](../brd/06-functional-requirements.md)–[BR-906](../brd/06-functional-requirements.md)) and the operating-model reporting cadence ([`operating-model.md` §Reporting cadence](../../company/operating-model.md)) into concrete screens, aggregation rules, and export contracts. Reporting here is a **derived, read-only projection** over the domain of record — every tile, figure, and pack traces back to a row the operator can open, and to the audit trail behind it ([NFR-04](../brd/08-nonfunctional-requirements.md)). Nothing in this surface mutates state.

**Framing rule:** reporting **surfaces obligations and evidence; it never discharges them, and it never produces the SOCPA opinion.** For Large/Medium waqfs the platform assembles the *evidence pack*; an external SOCPA auditor produces the audited statements ([BR-902](../brd/06-functional-requirements.md), [BR-906](../brd/06-functional-requirements.md)). The dashboard is a control panel, not a compliance certificate.

## 2 · Architecture — how reporting is computed

- **No separate reporting store in Phase 1.** Reports are computed on demand from the operational Postgres via **read-only tRPC query procedures** in `packages/api`, backed by pure aggregation helpers in `packages/domain` (`packages/domain` imports nothing internal). Money aggregates use `Decimal(18,2)`; **never floats, never client-side sums** — totals are computed server-side and returned formatted.
- **Every figure is drill-through.** A tile or report line carries the query filter that produced it; clicking resolves to the underlying rows (transactions, distribution line items, tasks, filings). Empty is a first-class state, not a zero.
- **KPI evaluation is an engine call, not a stored flag.** The five zero-tolerance KPIs (§4) are evaluated live by `packages/domain` against the compliance/deadline engine ([05 · Compliance & deadline engine](09-compliance-deadline-engine-spec.md)), the KYC state, the AML compartment, and the ledger. A KPI is never "green because someone marked it green."
- **Exports are materialized and hashed.** An evidence pack (§6) is a point-in-time snapshot: generated by an `apps/worker` pg-boss job, written to `packages/storage` (S3-compatible), content-hashed, and recorded as a `ReportArtifact` with the query parameters, generating user, coverage window, and SHA-256 digest — so a regulator can be told exactly what was produced, when, and that it has not since changed ([NFR-04](../brd/08-nonfunctional-requirements.md), [NFR-12](../brd/08-nonfunctional-requirements.md), [NFR-07](../brd/08-nonfunctional-requirements.md)).
- **Access-scoped at source.** Every reporting query runs through the same per-endowment access grant and beneficiary-isolation / AML-compartment filters as the rest of the app ([10 · Roles & access matrix](10-roles-access-matrix-spec.md)). A report can never widen visibility beyond the caller's grants; AML SAR existence never leaks into a KPI count for a non-compartment viewer.
- **Bilingual + dual-calendar.** All labels resolve through `packages/i18n`; every date renders **Hijri (Umm-al-Qura) + Gregorian**; SAR renders with Latin digits and `tabular-nums` ([NFR-01](../brd/08-nonfunctional-requirements.md), [NFR-02](../brd/08-nonfunctional-requirements.md)). Printable/exported artifacts use the light theme ([13 · UX & design system](13-ux-designsystem-reference.md)).
- **Configurable cadence & windows.** Cadence definitions, deadline windows, and classification thresholds are configuration, not code ([NFR-13](../brd/08-nonfunctional-requirements.md)).

## 3 · The compliance dashboard (BR-901) — layout

The operator's home surface, scoped to one endowment (with an all-my-endowments roll-up for multi-assignment staff). Six regions, top-to-bottom by urgency:

### 3.1 KPI strip (top, always visible)
Five status chips — one per zero-tolerance KPI (§4) — rendered `success` / `warning` / `danger`. **Danger dominates:** any red KPI turns the endowment header marker red and pins the offending items to the top of "Decisions required." KPI chips are **never dismissible** and never cached stale (recomputed on load and after any material action).

### 3.2 Deadlines — upcoming & overdue
A time-ordered list from the deadline engine ([05](09-compliance-deadline-engine-spec.md)): statutory items (register 30 bd, update 15 bd, istibdal notice 10 bd, distribute within 3 months of FYE, retain ≥10 yr) plus templated obligations. Each row: obligation, **Hijri + Gregorian due date**, **KSA business-days remaining** (Sun–Thu workweek, Hijri-moving holidays honored), status, owner. Buckets: **Overdue** (danger) → **Due ≤ 15 bd** (warning) → **Upcoming**. Classification gating applies — obligations that don't apply to the endowment's class are not shown.

### 3.3 KYC freshness
Beneficiary/UBO verification state roll-up: counts of **current / expiring / stale / never-verified**, with the distribution-blocking implication called out (a stale/unverified beneficiary or an uncaptured beneficiary category **blocks that line item** in a distribution run — see [04 · Distribution engine](08-distribution-engine-spec.md)). UBO rows are flagged distinct from ordinary beneficiaries.

### 3.4 AML flags (compartment-gated)
Visible **only** to AML-compartment members ([10 §AML compartment](10-roles-access-matrix-spec.md)). Shows open/under-review SAR items as *"a report was filed"* status — **no subject identity, no tipping-off**, no outbound detail. To every non-member the region does not render at all (not greyed, not count-only). A filed-but-overdue internal review is a `warning`; **a missed AML report is a red zero-tolerance KPI** (§4).

### 3.5 Government filing statuses
Manual status fields (Awqaf Digital, Baladi, Istihkam, Muqeem, Qiwa, Ejar) — **not live integrations** ([09 · Data & integration landscape](../brd/09-data-integration-landscape.md)). Each: platform, status (`not_started` / `in_progress` / `submitted` / `accepted` / `rejected` / `n_a`), last-updated (who/when), linked evidence document. Rejected or stale-past-deadline escalates into Deadlines and, where statutory, into the registration/update KPI.

### 3.6 Decisions required
The action queue: reserved matters awaiting Nazir sign-off, distribution runs awaiting maker→checker approval, filings awaiting submission, KYC re-verifications overdue. Each routes to the owning workflow; each carries its SoD state (maker ≠ checker) so the viewer sees whether *they* are eligible to act.

## 4 · The five zero-tolerance KPIs — evaluation rules

Sourced verbatim from [`operating-model.md`](../../company/operating-model.md) and [BR-901](../brd/06-functional-requirements.md). Each is `success` unless a stated breach/at-risk condition holds. **There is no manual override to green.**

| # | KPI | `danger` (breach) | `warning` (at risk) | Evidence source |
|---|---|---|---|---|
| 1 | **On-time Authority registration & updates** | Any statutory register/update/istibdal-notice deadline **passed** without an accepted filing | Deadline within its window and filing not yet submitted | Deadline engine + filing status |
| 2 | **No commingling** | Any transaction touching a **non-dedicated / shared** account, or a waqf without a dedicated account on file | Dedicated account unverified/expired | Ledger + bank-account register ([BR-506](../brd/06-functional-requirements.md)) |
| 3 | **Current beneficiary KYC** | Any beneficiary/UBO **stale or never-verified** on an endowment with pending/active distribution | Verification expiring ≤ its refresh window | KYC state ([04](08-distribution-engine-spec.md)) |
| 4 | **No missed AML/CTF reports** | An internal suspicion flagged and its reporting deadline **passed** without a recorded report | Suspicion open, deadline approaching | AML compartment (existence only) |
| 5 | **No unlicensed regulated real-estate activity** | A regulated real-estate action recorded against an **unlicensed** entity/subcontractor | Licence expiring / verification pending | Entity licence register ([BR-603](../brd/06-functional-requirements.md)) |

KPI 4's evaluation runs inside the AML compartment; for non-members the chip still renders (it must, or its absence would tip off) but resolves from a **compartment-computed boolean** with no readable detail.

## 5 · Financial reporting (BR-902) — class-appropriate

### 5.1 The four core reports
All scoped per endowment, per fiscal period, **reconciling to bank** ([NFR-14](../brd/08-nonfunctional-requirements.md)); official financial records render in **Arabic** ([NFR-01](../brd/08-nonfunctional-requirements.md)); money as `Decimal(18,2)`.

1. **Cash position** — opening/closing balance per **dedicated** waqf account, movements, reconciliation status. Commingling shows as a red exception, not a silent line.
2. **Revenue & expense** — ghallah (income) and operating/management/ṣiyāna (maintenance) costs by category and period; the input to the distribution waterfall.
3. **Distributions** — distribution runs and line items: gross ghallah → **ṣiyāna reserved first** → operating/management cost → **Nazir fee** (deed-set, default 10% of revenue = ʿushr; basis `percent_of_revenue | percent_of_net_income | retainer`) → **distributable**, then per-beneficiary payout by tier (ṭabaqa) / line (ẓuhūr–buṭūn). Blocked line items (stale KYC, uncaptured category, unlicensed disburser, cross-border pending) show *why*. **Direct-utilization waqfs have no monetary distribution** — the report states this rather than showing zeros.
4. **Arrears** — receivables past due (e.g. rent roll from property management), aged, with follow-up status.

### 5.2 Classification gating (BR-902)
The report set the platform produces depends on the Authority classification ([glossary §B](../../domain/glossary.md)):

| Class | Platform produces | External step |
|---|---|---|
| **Large / Medium** | Full **evidence pack** (§6): reconciled financials, ledgers, supporting documents, budgets, bylaws, periodic beneficiary statements | **External SOCPA auditor produces the audited statements** from the pack — platform never emits an "audited" opinion |
| **Small** | **Simplified annual statement** (self-contained) | No external audit required |
| **Direct-utilization (ذات انتفاع مباشر)** | Simplified annual statement; **no distribution reporting** (beneficiaries use the asset itself) | — |

The class flag drives which report actions are offered; requesting a report inapplicable to the class returns a clear "not applicable for this classification" state, not an empty document.

## 6 · Evidence-pack export (BR-906, BR-905) — the auditor/regulator surface

### 6.1 Purpose & delivery posture
An **on-demand, point-in-time bundle** of financials plus supporting evidence, produced *by the platform* and delivered **out-of-band** (download/upload) — consistent with the manual-integration posture; **there is no live regulator/auditor API integration** ([09](../brd/09-data-integration-landscape.md)). "Without engineering effort" is the requirement ([NFR-12](../brd/08-nonfunctional-requirements.md)): an operator generates it self-service.

### 6.2 The REST/OpenAPI surface
Evidence packs and disclosure exports are exposed via the **thin REST/OpenAPI layer** (the regulator/auditor-facing surface), *not* the internal tRPC API, so an auditor tool or scoped token can consume a stable, versioned, documented contract:

- `POST /v1/exports/evidence-pack` — body: `{ waqfId, periodStart, periodEnd, includeSections[], locale, format }` → returns `{ artifactId, status: "queued" }` (async; enqueues a pg-boss job).
- `GET /v1/exports/{artifactId}` — returns `{ status, sha256, coverage, generatedBy, generatedAt, downloadUrl (expiring), manifest[] }`.
- `GET /v1/exports/{artifactId}/download` — the bundle (ZIP: PDF report set + source documents + a JSON/CSV manifest).
- Auth: scoped bearer token bound to an **auditor**/**regulator** grant with an **engagement window** ([10 §Oversight](10-roles-access-matrix-spec.md)); TOTP-gated issuance; every access **audit-logged**, including the download event.

### 6.3 Contents & integrity
A generated pack contains: the class-appropriate financial reports (§5), reconciled ledgers, linked supporting documents (deed, filings, receipts, bank confirmations) from `packages/storage`, the distribution run detail, and a **manifest** listing every item with its hash. The whole bundle is SHA-256 hashed and recorded as a `ReportArtifact` (immutable, ≥10-year retention, [NFR-07](../brd/08-nonfunctional-requirements.md)). Re-running for the same window produces a **new** artifact (never overwrites) so the chain of what-was-shown-to-whom is preserved.

### 6.4 Beneficiary/UBO disclosure export (BR-905)
A dedicated export mode producing the **Beneficial-Ownership minimum dataset** and beneficiary register for Authority/audit disclosure. UBO rows flagged distinct; **AML SAR existence is never included** (no-tipping-off holds even in disclosure exports). P2 alongside portal, but the export contract is defined here so §6.2 covers it as an `includeSections` option.

## 7 · Portfolio view (BR-904) — leadership

A leadership-role dashboard variant ([10](10-roles-access-matrix-spec.md), role `leadership`) aggregating across clients → waqifs → endowments the caller is granted: count of endowments by KPI health (red/amber/green roll-up), overdue-deadline totals, distributions-due-this-quarter, and arrears exposure. **Read-only, no per-endowment operational write.** Beneficiary PII and the AML compartment do **not** roll up into the portfolio view. P2.

## 8 · Cadence packs (BR-903) — defined now, scheduled Phase 2

Per [`operating-model.md` §Reporting cadence](../../company/operating-model.md). Defined here so the export engine (§6) and data model are cadence-ready; **generation/scheduling/delivery is Phase 2** (depends on the portal). Each pack is a parameterized evidence-pack profile (an `includeSections[]` preset + recipient + cadence).

| Pack | Cadence | Recipient | Contents | Phase |
|---|---|---|---|---|
| **Operations pack** | Monthly | QMULATE (internal) | Operations, cash, rent roll, arrears, maintenance, risks, decisions + evidence pack | Profile P1 · scheduled **P2** |
| **Board pack** | Quarterly | Family Board (Principal) | Financial statement, KPI dashboard, property status, beneficiary issues, compliance calendar (+ Q&A session, off-platform) | Profile P1 · scheduled **P2** |
| **Annual pack** | Annual | Beneficiaries & Authority | Audited financials **or** simplified annual statement (by class), beneficiary disclosure, Authority filing (+ General Meeting, off-platform) | Profile P1 · scheduled **P2** |

Scheduling uses `pg-boss` in `apps/worker` on Railway Cron; annual timing anchors to fiscal-year-end and honors the **3-month distribution deadline**. Cadence definitions are configuration ([NFR-13](../brd/08-nonfunctional-requirements.md)).

## 9 · Acceptance criteria (Given / When / Then)

### 9.1 Compliance dashboard — KPI evaluation

- **Happy path:** *Given* an endowment with all filings accepted on time, dedicated bank account verified, current KYC, no open AML suspicions, and licensed subcontractors, *When* the case manager opens the dashboard, *Then* all five KPI chips render `success` and the endowment header marker is neutral.
- **Breach dominates:** *Given* a statutory update deadline passed without an accepted filing, *When* the dashboard loads, *Then* KPI 1 renders `danger`, the header marker turns red, and the overdue filing is pinned to the top of "Decisions required."
- **At-risk edge:** *Given* a beneficiary KYC expiring in 10 days on an endowment with a pending distribution, *When* the dashboard loads, *Then* KPI 3 renders `warning` and the KYC-freshness region counts that beneficiary as "expiring," and the distribution preview flags the line item as at-risk.
- **AML no-tipping-off:** *Given* an open SAR on the endowment, *When* a `case_manager` (non-compartment) opens the dashboard, *Then* the AML region does not render at all and KPI 4 resolves from a compartment-computed boolean with no readable detail; *And When* an `aml_officer` opens it, *Then* the AML region renders the "report filed" status without subject identity.
- **Empty state:** *Given* a newly onboarded endowment with no transactions or tasks yet, *When* the dashboard loads, *Then* each region shows an explicit empty state (e.g. "No obligations scheduled yet") — never a misleading all-green or a zero total.
- **Error state:** *Given* the deadline engine cannot compute (e.g. missing FYE), *When* the dashboard loads, *Then* the Deadlines region shows a blocking error prompting the missing input, and KPI 1 renders `warning` (indeterminate ≠ green), never silently `success`.
- **Freshness:** *Given* an operator completes a filing submission, *When* they return to the dashboard, *Then* KPIs and deadlines are recomputed (no stale cached green).

### 9.2 Evidence-pack export

- **Happy path:** *Given* a `finance` user with a grant on a Medium-class endowment, *When* they `POST /v1/exports/evidence-pack` for the last fiscal year with TOTP, *Then* a job is enqueued, the pack is generated (class-appropriate report set + linked documents + manifest), a `ReportArtifact` is recorded with SHA-256 + coverage + generatedBy, and the access is audit-logged.
- **Class gating:** *Given* a Small-class endowment, *When* an evidence pack is requested, *Then* the bundle contains the **simplified annual statement** and is not labeled "audited"; *And* for a direct-utilization waqf, *Then* the pack omits distribution reporting and states the direct-utilization basis.
- **Scoped auditor access:** *Given* an `auditor` token bound to an engagement window, *When* it `GET`s an artifact inside the window, *Then* the download URL resolves; *And When* the window has closed, *Then* the request is denied and the denied attempt is audit-logged.
- **Integrity / immutability:** *Given* an existing artifact for a window, *When* the same window is re-exported, *Then* a **new** artifact with a new hash is created and the prior one is retained unchanged (≥10-year retention).
- **No tipping-off in disclosure:** *Given* an open SAR, *When* a beneficiary/UBO disclosure export (BR-905) is generated, *Then* the bundle contains the BO minimum dataset but **no** reference to the SAR's existence.
- **Access boundary:** *Given* a user without a grant on the target endowment, *When* they request its evidence pack, *Then* the request is denied (deny-by-default) and logged; no data leaks in the error.
- **Empty/partial:** *Given* a requested period with no transactions, *When* the pack generates, *Then* it produces a valid bundle with explicit "no activity in period" sections rather than failing or emitting an empty file.
